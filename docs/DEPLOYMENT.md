# 部署与下一步联调

目标域名：**image.yidianhub.com**；品牌：**Yidian-Image**。

## 当前状态

本地已连接现有 New API，已有人工作业样例验证 GPT Image 2 的标准单张方图生成、参考图编辑和局部重绘。模型只开放该范围；实测输出为 1254×1254，不保证按请求值精确返回像素。详见 [首轮试用检查](PILOT_REVIEW_2026-11-12.md)。真实收款仍关闭；未操作服务器、DNS、证书或现有中转站配置。

## 选择部署方式

当前已选定 **GitHub Actions 构建、GHCR 发布镜像、服务器拉取指定版本**。仓库为 `zhuyidian/image-studio`，生产部署请按 [GitHub Release 部署流程](GITHUB_RELEASE_DEPLOYMENT.md) 操作；服务器无需上传源码或执行 build。

如果现有 HTTPS 由 Docker 容器 `yidian-api-caddy-1` 管理，请使用 [接入现有 Docker Caddy](EXISTING_CADDY.md) 的独立 Compose 文件。此情形不适用下面“宿主机代理访问 127.0.0.1”写法。

### 已有 Nginx / 宝塔 / Caddy

1. 将本项目放入独立服务器目录，不覆盖 New API。
2. 将 `deploy/production.env.example` 复制为项目根目录 `.env.production`，填写真实参数。
3. 执行 `docker compose up -d --build app`。
4. 已有反向代理将 `https://image.yidianhub.com` 转发到 `http://127.0.0.1:8787`。
5. 代理需支持 21MB 请求体和至少 60 秒读取超时。图片生成本身在 Worker 中执行，不占用浏览器长请求。
6. `TRUST_PROXY_HOPS=1` 仅适用于 API 只经过这一个可信代理且不能被绕过访问的部署。存在 CDN 或其他代理时，需要按实际拓扑配置，不能直接信任任意 X-Forwarded-For。

### 新服务器，使用自带 Caddy

1. 将域名解析到已准备好的服务器，确保 80/443 没有被现有服务占用。
2. 准备 `.env.production`。
3. 执行 `docker compose --profile https up -d --build`。
4. Caddy 为 `image.yidianhub.com` 申请证书并转发到应用。现有服务器若已经运行 HTTPS 代理，不要启动这个 Caddy 服务。

Compose 不包含现有 New API，它通过你填写的 HTTPS 地址连接，不会改动中转站数据库。

## 首次生产管理员

首次在受限访问环境中配置好 SMTP，临时开放注册，验证邮箱并注册自己的账户，然后提升为管理员。容器包含编译后的管理命令，无需安装开发依赖：

```bash
docker compose exec app node dist/scripts/admin.js registration true
# 在网站完成邮箱验证并注册后：
docker compose exec app node dist/scripts/admin.js promote YOUR-ADMIN-EMAIL
# 暂停公开注册（或以后在后台“注册与邮箱”关闭）：
docker compose exec app node dist/scripts/admin.js registration false
```

不要在公共环境保留演示账号或使用已公开的固定管理员密码。生产构建不提供演示登录接口。

`ALLOW_REGISTRATION` 只在账户设置首次初始化时使用；数据库已有设置后，修改环境变量不会覆盖后台选项。上面的服务器终端命令可以处理尚未设置首位管理员、无法进入后台时的注册开关。它不会跳过邮箱验证，不修改已有用户积分或密码；请仅在受信任的服务器终端操作。

## 必须完成的实际联调

- **New API**：确认部署版本、模型 ID、生成/编辑协议、质量字段、多图限制与响应格式。在“模型管理”逐项配置，通过“测试模型”或工作台的管理员测试开关进行验证，再决定向用户开放；测试入口允许管理员调用未验证/停用配置，但不会自动将其上架。真实测试会产生上游费用并正常结算管理员积分。
- **计费**：用实际成本测算积分价格，避免把示例积分包直接作为正式商业报价。
- **支付**：确认是 EPay 兼容商户，还是微信 V3/支付宝 RSA2 官方直连。当前适配仅覆盖前者。先小额检查签名、重复通知、金额、付款方式、到账、退款与对账。
- **结果不明**：演练上游超时、应用重启和人工核对，确认不会无条件重试生成。
- **公开注册**：已实现邮箱验证、找回密码、用户禁用、IP/邮箱基础频率限制。当前只有本地测试邮件，生产必须配置并验证 SMTP，另按实际流量补验证码和风控。生产初始设置默认关闭注册、赠送积分为 0；之后通过后台“注册与邮箱”管理。详见 [账户与邮件](ACCOUNTS.md)。
- **图片内容**：当前上传只验证格式/尺寸并重新编码；并未接入独立内容审核服务。应接入你的审核策略，不能只依赖上游拒绝。
- **数据维护**：已支持作品单项/批量删除、回收站恢复、永久清除、图片用量和后台统一限额/保留策略。默认作品不自动过期、回收站保留 30 天，详细规则见 [作品与存储](STORAGE.md)。上线前按实际服务器空间调整并验证目录权限、清理和备份。

## 备份和恢复

SQLite 与 `media/` 必须一起备份。源码开发环境可以执行：

```powershell
npm run backup
npm run backup -- verify "备份目录的完整路径"
```

备份工具使用 SQLite backup API 读取一致快照（包含已提交 WAL 数据），复制该快照中仍可访问的媒体并生成摘要清单；验证同时检查数据库、外键、余额与账本、媒体 SHA-256。备份与物理清理共用进程间文件锁，防止复制时图片被删除；已清除作品的账务记录仍保留，但不要求备份已清除的图片。图片文件保存后不改写，可在服务运行时备份。

备份输出位于私有 `data/backups/`，包含用户与图片数据，不应提交 Git 或公开下载。备份不包含 `.env`，密钥配置需单独私密保存。生产镜像也包含编译后的备份模块，可通过运维脚本调用；最简单的生产备份仍是在维护窗口停止 app 后备份整个 `studio-data` 卷，随后启动。不要只复制正在写入的 `.sqlite` 主文件而忽略 WAL。

恢复时应恢复完整的数据目录，保留媒体文件名与数据库对应关系。启动会将遗留 running 任务转为 uncertain，保留冻结积分；queued 任务继续执行，不会自动重提 running 任务。

## 当前部署边界

- 单 API/Worker 实例 + 单 SQLite 数据库 + 本地持久卷，适合小规模验证。
- 单机文件存储尚未接入 S3/OSS/R2。跨服务器部署前应增加对象存储适配。
- 已有多模型目录、能力选择与独立定价，以及验证码/密码重置邮件能力；当前只接同步 Images 协议。缺少供应商异步任务轮询、自动对账、退款、团队席位和订阅续期。真实 SMTP 仍需配置验收。
- 生产应用可通过 `npm run build` 检查；本机 Docker 守护进程未开启时无法验证镜像构建，应在目标环境再次执行。

## 扩展顺序

先按已验证的标准单张能力进行少量用户试用，再打通选定支付商；确认成本和体验后逐个开放其他模型、增加对象存储和支付对账。出现多进程需求后迁移 PostgreSQL 和独立队列，避免一开始引入微服务。
